# MDNET 整体架构

## 1. 目标与仿真边界

MDNET 的目标是在一台或多台物理机上运行独立 Mininet 实例，接入 SDN 控制器，并将空天地、UAV–车网等信道模型产生的时变结果映射为可实际运行的网络环境。

该系统首先是一个**基于真实 Linux 协议栈的网络仿真器**，而不是波形级或完整 PHY/MAC 仿真器。其适用边界如下：

| 研究目标 | 方案 |
| --- | --- |
| 时变带宽、时延、抖动、丢包对业务和路由的影响 | Mininet + Linux `tc/netem`，是第一版的主要目标 |
| 关联、切换、共享频谱和链路间干扰 | 在模型层中引入共享介质和资源调度模型 |
| 802.11 竞争退避、MCS、MAC 重传等细节 | 将 Mininet-WiFi/wmediumd 或 ns-3 作为可选后端，不由 `tc` 单独承担 |
| 编码、调制、波形或物理层算法 | 不在 MDNET 核心范围内，由外部 PHY 仿真器提供结果 |

`tc` 实现的是信道对 IP 数据包的**等效影响**，不是完整的射频传播过程。这个边界必须在实验报告中明示。

Mininet-WiFi 本身也将 `tc` 与 wmediumd 视为两种不同的无线介质方案，后者才额外提供无线接口隔离、退避和基于信号强度的关联语义。([Mininet-WiFi][4]) ns-3 将传播损耗与传播时延分开建模，本架构继续采用这种可组合思路。([ns-3 propagation][5])

## 2. 设计决策

顶层保留“模型—编排—执行”三层边界：

1. **模型层**：管理移动性、传播、干扰、关联和资源分配，输出与 Mininet 无关的信道快照。
2. **编排层**：推进仿真时间，将物理量编译为后端可执行参数，并协调分布式 worker。
3. **执行层**：操作 Mininet、OVS、跨机隧道和 Linux `tc`，回报实际生效状态。

在三层内部强制保留两个边界：

- **信道模型 → 后端编译器**：物理量不直接等于 `tc` 参数。
- **编译器 → 执行后端**：执行后端只接收已确定的幂等操作，不计算信道公式。

这样既不破坏原有简洁分层，又避免将“理论容量”直接当成“Linux 限速值”。

## 3. 总体数据流

```text
场景配置 + 轨迹 + 业务需求
              ↓
       节点与无线电状态
              ↓
   覆盖/可见性 + 传播/衰落
              ↓
 共享介质 + 干扰 + 关联/资源调度
              ↓
        ChannelSnapshot
              ↓
       backend compiler
              ↓
        EmulationPlan
              ↓
 coordinator → worker → tc / OVS / tunnel
              ↓
  目标值 + 实际配置 + 实测结果
```

信道引擎应一次计算整个候选链路集，而不是在完全隔离的上下文中逐链路调用。否则无法正确表达共享频谱：一个 UAV 同时连接多辆车时，不能让每条链路都独立获得全部频谱容量。

## 5. 核心数据契约

### 5.1 信道快照

信道模型输出物理和链路能力量，不包含任何 Linux 接口名。

```python
@dataclass(frozen=True)
class DirectedRadioLinkState:
    link_id: str
    src_node_id: str
    dst_node_id: str
    reachable: bool
    rx_power_dbm: float | None
    sinr_db: float | None
    phy_rate_bps: int
    allocated_rate_bps: int
    propagation_delay_us: int
    packet_error_rate: float
    outage_reason: str | None = None


@dataclass(frozen=True)
class ChannelSnapshot:
    experiment_id: str
    epoch: int
    valid_from_s: float
    valid_until_s: float
    links: tuple[DirectedRadioLinkState, ...]
```

`phy_rate_bps` 表示依据频宽、SINR/MCS 得到的发送速率，`allocated_rate_bps` 表示共享介质调度后分配给该有向链路的整形速率。两者都定义在施加 `packet_error_rate` 之前，避免先在速率中扣除误包影响，又在 `netem` 中重复丢包。compiler 默认使用 `allocated_rate_bps` 生成 `rate_bps`。

### 5.2 批量信道接口

```python
class ChannelEngine(Protocol):
    def evaluate(
        self,
        time_s: float,
        nodes: Mapping[str, NodeState],
        radios: Mapping[str, RadioState],
        demand: TrafficDemandSnapshot,
        environment: EnvironmentState,
    ) -> ChannelSnapshot:
        ...
```

批量接口允许引擎联合计算干扰和资源分配。第一版可使用固定或配置的 `TrafficDemandSnapshot`；需要闭环时，使用上一个周期的接口统计作为下一周期输入。这是有一个周期延迟的近似，必须记录在实验元数据中。

### 5.3 后端执行计划

```python
@dataclass(frozen=True)
class LossPlan:
    kind: str                 # random / gemodel / trace
    probability: float
    correlation: float | None = None
    seed: int | None = None


@dataclass(frozen=True)
class EmulationPlan:
    experiment_id: str
    epoch: int
    operation_id: str         # 全局唯一，用于幂等与审计
    logical_link_id: str
    direction: str
    worker_id: str
    interface_ref: str        # registry key，不必等于接口名
    rate_bps: int
    delay_us: int
    jitter_us: int
    loss: LossPlan
    queue_limit_bytes: int
    link_state: str
```

`queue_limit_bytes` 作为后端的标准表达；若某后端只接受包数，由 compiler 根据 MTU 转换。队列默认值应与带宽时延积、实验所需的 AQM/FIFO 语义联系，不应任意固定。

## 6. 共享介质与业务闭环

信道干扰依赖“谁正在发射”，而发送行为又依赖信道状态。MDNET 将其显式定义为三种可选模式：

1. **open_loop**：根据预设负载和调度表计算；可重放性最强，作为 MVP 默认。
2. **lagged_feedback**：上一周期实测负载驱动下一周期；能表达简化闭环，但存在一个 tick 的滞后。
3. **external_scheduler**：由 ns-3、wmediumd 或其他外部模型输出分配结果；作为扩展点。

不在第一版实现事件级的完整 PHY/MAC 闭环。这会显著提高复杂度，也与 `tc` 的包级等效仿真定位不一致。

## 7. 时间模型与每轮流程

### 7.1 多速率时钟

不将 1 秒写成架构级固定步长。场景可分别配置：

```yaml
clock:
  mode: realtime
  mobility_tick_ms: 1000
  channel_tick_ms: 100
  scheduler_tick_ms: 100
  telemetry_tick_ms: 1000
  max_apply_skew_ms: 20
```

移动、信道、调度和采集可使用不同周期。快衰落通常不通过高频 shell/远程 `tc` 调用实现，而是编译为相关丢包、分布参数或预生成 trace。

### 7.2 每个 channel epoch

1. `coordinator` 生成单调递增的 `epoch`。
2. `mobility` 根据自身周期更新位置。
3. `connectivity` 通过空间索引、可见性和候选规则缩小链路集。
4. `ChannelEngine` 批量生成 `ChannelSnapshot`。
5. compiler 考虑底层基线和后端能力，生成 `EmulationPlan`。
6. coordinator 根据阈值和上一轮做差分，仅下发有意义的变化。
7. worker 幂等执行计划，回报成功、失败、实际生效值和生效时间。
8. recorder 记录模型输入、快照、计划、执行回执和测量值。

对连续数值使用绝对或相对变化阈值，对连通性使用滞回和最小持续时间，避免临界点附近频繁更新 `tc` 或端口状态。

### 7.3 分布式同步

所有计划都必须带 `experiment_id`、`epoch` 和 `operation_id`，worker 必须拒绝旧 epoch 并幂等处理重复操作。

提供两种同步策略：

- **best_effort**：发送后立即应用，记录各 worker 实际生效时间；适用开发和大规模低精度实验。
- **barrier**：先 `prepare(epoch)`，全部 worker 就绪后再 `commit(epoch)`；适用对跨机生效偏差敏感的实验。

不强制所有场景每轮都执行两阶段事务，因为其会带来显著控制开销。两种策略都必须定义超时时是中止实验、跳过本轮，还是将缺席 worker 标记为故障。

## 8. Linux `tc` 执行语义

### 8.1 有向参数归属

Linux shaping 主要发生在 egress。A→B 的参数原则上施加在 A 侧的发送出接口，B→A 施加在 B 侧。必须通过 registry 保证同一个方向不在 veth、OVS 端口和隧道端口上被重复施加，否则时延会叠加，丢包语义也会变化。

对 TCP 真实性要求较高的场景，可以增加 IFB，将接收端 ingress 重定向为可 shaping 的 egress。这应作为后端能力，而不是所有实验的强制要求。

### 8.2 qdisc 策略

后端不硬编码唯一 qdisc 结构，而是按 profile 选择：

```text
simple:    netem rate + delay/loss
shaped:    HTB/TBF → netem → FIFO/AQM
trace:     trace-driven loss/delay backend
```

worker 优先使用 `tc qdisc replace` 或 batch 更新，并在执行后读回 qdisc 状态。Linux `netem` 支持时延分布、相关或状态丢包、限速、时隙和随机种子，但其精度受内核定时器和原生承载网影响，因此必须通过黑盒测量验证。([tc-netem][2])

## 9. 链路状态机

单一 `available: bool` 不足以区分信道现象和仿真基础设施故障。至少定义：

```text
UP                 正常可用
DEGRADED           可用但质量下降
RADIO_OUTAGE       无线不可达，基础设施正常
UNASSOCIATED       不满足关联或切换规则
ADMIN_DOWN         实验显式关闭端口
TUNNEL_FAILURE     跨机承载故障
WORKER_FAILURE     执行节点故障
```

状态到执行行为的映射由场景决定：

- `RADIO_OUTAGE → 100% loss`：保持端口 up，用于观察协议超时和失联检测。
- `RADIO_OUTAGE → port down`：向控制器显式暴露链路事件，用于研究即时重路由。
- `TUNNEL_FAILURE/WORKER_FAILURE`：标记为实验运行异常，不计入信道断链结果。

不建议在每次短暂信道断开时删除并重建 veth 或隧道。优先预建可能的联系并切换数据面状态，以保持 OVS 端口号和 SDN 拓扑标识稳定。对大规模节点，预建的是时间窗内可能出现的候选图，不是完全图。

## 10. 逻辑链路、本机接口与跨机隧道

`link_registry` 维护如下关系：

| 对象 | 示例 | 用途 |
| --- | --- | --- |
| 逻辑链路 | `sat-03__uav-07` | 供模型、拓扑和日志引用 |
| 有向链路 | `sat-03__uav-07:a_to_b` | 参数和执行的最小归属单元 |
| 本机接口 | 短 ID，例如 `mdn0a13` | `tc`/OVS 执行目标 |
| 跨机承载 | worker pair + VNI/VLAN/key | 在物理机之间承载多条逻辑链路 |

接口名使用可重现的短编码，不直接拼接任意长度的节点 ID。信道模型不得依赖 `s1-eth3` 之类临时名称。

跨机承载支持两种实现：

- **per_link_tunnel**：隔离简单，但隧道数量随链路增长。
- **shared_tunnel**：每对 worker 共用隧道，但必须使用 VNI/VLAN、mark 或 `tc filter` 分类，否则无法对逻辑链路单独施加参数。

第一版先使用 `per_link_tunnel` 降低正确性风险，达到隧道规模上限后再切换为共享模式。

隧道封装会改变 MTU，设计和验收时必须检查分片或配置对应 MTU。Open vSwitch 的隧道文档也明确提醒需考虑物理网络和 MTU。([OVS tunneling][3])

## 11. 底层网络基线和准入检查

跨机物理网络已经具有时延、抖动、丢包和带宽上限。MDNET 可以在此基础上增加损伤，但不能可靠地模拟低于底层的时延或高于底层的带宽。

实验启动前必须：

1. 测量每对 worker 的基线 RTT、抖动、丢包和可用吞吐。
2. 验证场景目标在底层能力之内；不满足时拒绝运行或显式降级。
3. 记录基线，不默认“目标时延减去一次 RTT”；单向基线只能在时钟同步和测量可靠时扣除。
4. 将管理网、SDN 控制网和仿真数据网隔离；若研究 in-band control，必须作为显式场景配置。

## 12. SDN 交互语义

每个交换机必须有稳定 DPID，每条预建链路必须有稳定 OpenFlow 端口号。不应让短暂的信道衰落导致 OVS 端口被反复删除和新建。

场景必须声明控制器如何感知链路变化：

- 等待 LLDP/BFD/路由协议超时；
- 由 worker 切换 port state；
- 通过显式的拓扑事件 API 通知控制器。

这三种方式衡量的是不同问题，不能在同一组对比实验中混用。

## 14. 可观测性与可重放性

每轮保留以下四类数据，不只记录最终 ping/iperf3 结果：

1. **模型输入**：轨迹、环境、业务需求、seed。
2. **模型输出**：`ChannelSnapshot`。
3. **执行数据**：`EmulationPlan`、worker 回执、`tc/OVS` 读回值、实际生效时间。
4. **结果测量**：UDP 速率/丢包/时延、TCP 吞吐、队列和接口计数器。

同时保留代码提交、配置文件、模型版本、Mininet/OVS/iproute2/Linux kernel 版本和底层基线。重放的目标分为：

- **计划级确定性**：相同输入生成完全相同的 snapshot 和 plan。
- **网络级统计一致性**：真实内核调度下的包级结果允许存在抖动，但必须落在定义的统计误差范围内。

## 15. 测试与验收

### 15.1 单元测试

- 距离、坐标、dB/线性值和时间单位转换。
- 传播损耗、SINR、PER 与已知解或基准数据一致。
- 双向链路不得相互覆盖。
- 共享介质下的分配总量不超过可用资源。
- compiler 在不同 backend capability 下正确降级或拒绝。

### 15.2 后端符合性测试

- 先使用 UDP 分别验证 rate、delay、jitter、loss，再验证组合效果。
- 比较“计划参数—`tc` 读回值—黑盒实测”三者。
- 验证 A→B 和 B→A 的非对称参数，检查时延未重复施加。
- 验证 MTU、大包、分片和 tunnel overhead。
- TCP 只用于上层效果验收，不作为后端单项参数的唯一判据。

Mininet 支持通过 TCLink/TCIntf 设置链路带宽、时延和丢包，但端到端结果会累计路径上各段的影响，因此后端符合性测试是必需的。([Mininet walkthrough][1])

## 16. 分阶段实施路线

### Phase 0：数据契约和离线模型

- 实现 `schema.py`、schema 校验和单位系统。
- 实现一个距离驱动的基础模型。
- 生成并回放 `ChannelSnapshot`，不接入 Mininet。

### Phase 1：单机两节点

- 实现 `linux_tc` compiler、Mininet 和 `tc` backend。
- 使用单向 UDP 验证动态 rate/delay/loss。
- 扩展到双向非对称链路和断链状态机。

### Phase 2：单机共享介质

- 实现最小 `medium/scheduler`。
- 三节点或多流场景中，验证分配总量不超过介质容量。
- 加入变化阈值、滞回和差分下发。

### Phase 3：OVS 和 SDN 控制器

- 固定 DPID 和 OpenFlow 端口号。
- 分别验证 `loss_100`、`port_down` 和拓扑事件的控制面效果。

### Phase 4：两个 worker 的跨机仿真

- 先使用 `per_link_tunnel`，完成基线和 MTU 检查。
- 实现 epoch、幂等操作和 best-effort 生效时间记录。
- 只在实验对同时性敏感时增加 barrier 模式。

### Phase 5：扩展精度与规模

- 引入具体 UAV/卫星模型、干扰和闭环负载。
- 当隧道数量成为瓶颈时，实现 `shared_tunnel` 和分类整形。
- 若研究问题确实依赖 MAC 竞争或 PHY 细节，再增加 Mininet-WiFi/wmediumd 或 ns-3 适配器。

## 17. 经批判后的取舍

本架构接受了以下关键修正：

- 明确 `tc` 是包级等效仿真，不把系统过度声称为完整无线 PHY/MAC 仿真。
- 从逐链路计算改为批量 snapshot，增加共享介质和资源分配。
- 分离物理/链路状态与 Linux 执行计划。
- 增加 epoch、幂等、多速率时钟、跨机基线和后端符合性验证。

但不做以下过度承诺：

- **不默认每轮使用分布式两阶段事务**：它作为高精度可选模式。
- **不将 HTB/TBF 或 IFB 写死为唯一实现**：不同速率、内核和实验目标需要不同 qdisc profile。
- **不在 MVP 中引入完整 ns-3/wmediumd 协同仿真**：先建立稳定契约和可验证的 `tc` 后端。
- **不预建全完全图**：只预建可预见的候选接触，避免接口、OVS 端口和隧道数量呈平方增长。
